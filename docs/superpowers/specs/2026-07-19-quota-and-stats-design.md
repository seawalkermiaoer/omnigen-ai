# 用户算力配额与用量报表

- 日期：2026-07-19
- 分支：`rewrite-react-go`
- 前置：子项目 1–4 已完成（认证、配置、生成核心、历史记录）

## 背景

系统现在是多用户 + 共享一套上游 API Key。任何登录用户都能无限次调用模型，花的是同一份额度，管理员没有任何手段限制或观察消耗。

本文覆盖两个相关但独立的功能：

1. **算力配额** —— 每个用户有请求上限，每次生成扣 1，用完即止
2. **用量报表** —— 在历史页看到按模型、按天的调用统计

两者读写同一张 `generation_tasks` 表，但**配额是当前状态，报表是历史聚合，互不依赖**。这一点是刻意的：删除历史任务会改变聚合数字，但绝不能因此改变用户余额。**不得用报表聚合反推当前余额。**

# 第一部分：算力配额

## 已确定的决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 计费口径 | 按次数，一律扣 1 | 最简单、用户一看就懂。加权定价可以以后平滑追加 |
| 配额周期 | 一次性额度，管理员手动调 | 自用/小团队规模，无需定时任务与周期边界判断 |
| 计费范围 | 只扣生成，prompt 优化免费 | 优化是为了让生成一次就对，扣它会逆向激励——用户跳过优化、生成更差、重试更多次，反而更贵 |
| 失败处理 | 提交时扣，失败退回 | 上游报错、网络掉线、密钥失效都不该算到用户头上 |
| 管理员 | 默认不限量 | 管理员本就能改配置和别人的额度，限制他没有实际边界意义 |

## 数据模型

```sql
ALTER TABLE users
  ADD COLUMN quota_total INT,                        -- NULL = 不限量
  ADD COLUMN quota_used  INT NOT NULL DEFAULT 0;

ALTER TABLE generation_tasks
  ADD COLUMN quota_charged BOOLEAN NOT NULL DEFAULT false;
```

**`quota_total` 用 NULL 表示不限量**，不用 `-1` 这类魔法值——SQL 里 `quota_total IS NULL OR quota_used < quota_total` 读起来就是它的字面意思。

**`quota_charged` 用于防重复退款。** 视频是异步的，轮询 worker 在判定失败时退回；worker 若因任何原因重跑同一任务，没有这个标志就会退第二次，凭空给用户送额度。扣减时置 true，退回时以它为条件并置回 false —— 两个操作都因此幂等。

## 扣减必须是单条 SQL

先查余额再写入会超发：两个并发请求都读到「还剩 1」，都通过检查，都扣减。

```sql
UPDATE users SET quota_used = quota_used + 1, updated_at = now()
WHERE id = $1 AND (quota_total IS NULL OR quota_used < quota_total)
```

`RowsAffected = 0` 即额度不足。一条语句天然原子，不需要事务也不需要显式锁。

退回同理，并以 `quota_charged` 为条件：

```sql
UPDATE users SET quota_used = quota_used - 1, updated_at = now()
WHERE id = $1 AND quota_used > 0
```

配合把对应任务的 `quota_charged` 置 false，两者在同一事务内完成。

**放弃的方案：流水表。** 每次扣减/退回记一行，审计更完整。但 `generation_tasks` 已经逐条记录了每次生成，余额对不上时可直接对账，再加一张表是重复。

## 扣减点与退回点

| 时机 | 动作 |
|---|---|
| 参数校验失败、模型不存在、地域不允许、凭证未配置 | **不扣**——请求根本没发出去 |
| 提交生成（图片/视频），校验全部通过后、调用上游前 | 扣 1，置 `quota_charged = true` |
| 图片同步调用失败 | 当场退回 |
| 视频轮询判定 FAILED 或超时 | worker 退回 |
| prompt 优化 | 不扣 |

**顺序是设计的一部分**：扣减放在所有校验之后、真正调上游之前。校验失败不该动额度；而一旦要发请求，就必须先扣才能防并发超发。

## 接口与界面

- 新错误码 `QUOTA_EXCEEDED`（403），中英文案说明额度已用尽、请联系管理员。必须同时加入两份 locale 文件与 `locales.test.ts` 的覆盖列表。
- `GET /api/auth/me` 响应增加 `quotaTotal`（可为 null）与 `quotaUsed`
- 用户管理页：列表加「额度」列显示 `已用/总额`（不限量显示「不限」）；新建与编辑表单加额度输入，留空表示不限量
- 顶栏用户菜单旁显示剩余次数；不限量则不显示

# 第二部分：用量报表

## 位置与权限

`/history` 页面改为两个 Tab：**记录**（现有列表）与**报表**。不新增路由。

`GET /api/stats?from=&to=&userId=`

- 非管理员：`userId` 参数一律忽略，只返回本人数据
- 管理员：不传 `userId` 时看**全部用户合计**；传则筛选指定用户

## 聚合在 SQL 里做

不在 Go 里循环，更不在浏览器里算。浏览器只拿得到当前分页的几条记录，据此算出的「总统计」是错的；任务量增长后全量拉进内存也不合理。

返回三块：

| 块 | 内容 |
|---|---|
| 总览 | 总调用数、成功数、失败数、Token 合计、视频总时长 |
| 按模型 | 每个模型的调用数、成功率、Token、时长 |
| 按天 | 时间序列，每天的调用数与成功/失败拆分 |

时间筛选：预设「近 7 天 / 近 30 天 / 全部」+ 自定义区间。

## Token 数据的真实可得性

**这是本功能最容易做出误导性界面的地方。** 三个上游返回的 `usage` 结构不同：

| 模式 | `usage` 实际内容 |
|---|---|
| 图片（DashScope） | `total_tokens` / `input_tokens` / `output_tokens` / `image_count`，但部分模型只给 `image_count`，`total_tokens` 为 0 |
| 图片（t8star） | OpenAI 兼容格式，通常有 `prompt_tokens` / `completion_tokens` / `total_tokens` |
| 视频（三种全部） | **没有 token**。只有 `output_video_duration` / `SR` / `ratio` |

因此：

- SQL 中按 `COALESCE((usage->>'total_tokens')::numeric, 0)` 取值并求和
- **界面必须区分「没有 token 数据」与「token 为 0」**。视频行的 Token 列显示「—」而非 `0`，否则会让人误以为视频免费。表头注明视频不返回 token。
- 视频的真实用量口径是**时长**，单独成列

## 测试要点

### 配额

- **并发扣减不超发**：N 个 goroutine 同时抢最后 1 个额度，断言只有 1 个成功。这是本功能唯一的并发正确性要求，必须真的并发跑，不能用串行调用假装。
- 额度耗尽返回 `QUOTA_EXCEEDED`，且**没有真的发请求给上游**（用假 provider 断言调用次数为 0）
- 失败退回后余额复原
- **重复退回只生效一次**——直接调用退回两次，断言余额只加 1
- `quota_total IS NULL` 的用户永远不被拦
- 校验失败（模型不存在、地域不允许、凭证未配置）不扣额度
- prompt 优化不扣额度

### 报表

- 聚合结果与逐条数据对得上（造 N 条已知任务，断言总数、按模型、按天三者自洽）
- 非管理员传 `userId` 拿到的仍是自己的数据，不是别人的
- 管理员不传 `userId` 得到全部用户合计
- 时间边界：`from`/`to` 是闭区间还是半开区间需明确并测试，避免跨天记录被重复计入或漏计
- 视频任务的 Token 列返回「无数据」而非 0
- 空数据集返回结构完整的零值，前端不崩

## 明确不做

- 加权计费（按模型/时长/分辨率算不同成本）。当前一律扣 1，以后需要时再加。
- 配额周期性重置。
- 配额流水表 / 审计日志。
- 报表导出。历史记录已有导出 JSON，报表暂不需要。
- 用量预警、超额通知。
